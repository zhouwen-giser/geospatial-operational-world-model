# GOWM 功能缺口修复与交付计划

日期：2026-10-11，完成记录：2026-10-12。状态：R0–R5 已完成本地实施、针对性验证和部署包交付。现场和跨仓业务验收未执行，远端 exact-head CI 尚未运行。

## 1. 基线、目标与边界

代码基线：`506315b5a60e5f5fe405f020f61cec24be0be47d`，正式迁移头为 086。
问题及复现证据见 [功能落实检查](../reports/functional-audit-2026-10-11/README.md)。
该检查覆盖本地代码和隔离 PostgreSQL，没有重新确认 sz-gowm 或其他仓库的当前运行状态。

本轮优先交付五项实际缺陷 F01–F05 的修复，以及原生业务存储自动就绪、必要的 CI 门禁和部署包。
高级历史能力、通用采集及生产运行能力分为后续里程碑，各自验收，不混记为本轮修复完成。

持续遵守以下约束：

- 仅修改 GOWM；沿用现有分支和提交历史。
- 保持固定共享 `ugv_smpp`、`ugv_sdar`，业务写入显式携带 `device_id`。
  不新增实例级业务库、`business_store` 或业务数据导出同步链。
- 001–086、已发布原生迁移及已执行 GOWM overlay 的内容、身份和摘要保持不变；数据库改动追加迁移。
- 保持旧 mapper、持久采集会话、事件 actor、冻结请求及旧轨迹/分析结果的兼容性，不回填历史 actor。
- 保持真实缺口、`PROVISIONAL/PENDING`、租约代际和 30 秒裁剪预算。
  `RESET_ACK_ACCEPTED_COMPLETE_V1` 仍只表示已认可的允许少量丢包与迟到策略，不替代其他封存条件。
- 本轮不部署 sz-gowm，不运行现场恢复，不清零尝试次数、不重建耗尽队列、不改写旧快照。
  后续上线必须单独授权，并保护其他容器、数据库、卷、密码及服务绑定。

## 4. R1：统一默认范围与服务绑定接线

### 4.1 默认范围

- 全新开发部署统一使用已有 `default` 数据范围：UGV、Gateway principal 和 H3 accepted scope 一致。
  调整 `.env.example`、CLI/服务默认值、Compose fallback 和说明，消除不同组件各自补默认值的情况。
- 既有 `.env` 中显式配置的范围保持原样；不在升级时把 `airport-sim-ugv-01` 自动改成 `default`。
  `init_env` 只填缺失配置；有显式不一致时输出字段级错误和适配步骤。
- 数据集授权按既有 Catalog 映射单独校验，不将 dataset claim 与 data scope 当作可随意互换的标识。
- 保留 `default` 的现有 TEST 分类及采集端现有兼容规则，不重分类已有范围。
  实际发送一条合法 UGV 观测验证落库、actor 和授权查询，不能只验证设备初始化成功。
- 部署检查分为不接库的配置预检和迁移后、启动消费者前的只读数据库检查。
  后者核对实际范围、来源、世界对象、设备、流与 Gateway 授权的一致性。
- 保留 H3 单范围保护。存在多个范围时，明确阻止宣称 H3 已就绪；不删除空范围、不搬运已有数据，
  也不通过去掉检查开放未隔离的聚合。需要多范围 H3 的安装进入后续 H3 改造里程碑。

### 4.2 服务变量

- 转发并记录六项配置：`SMPP_SERVICE_KEY`、`UGV_PROVIDER_ID`、`UGV_RESOURCE_ID`、
  `SDAR_SERVICE_KEY`、`SDAR_MCP_SERVER_ID`、`SDAR_AGENT_PROFILE_ID`。
- SMPP 三项成组；SDAR service/server 成组；agent profile 只能随有效 SDAR 配置使用。
  不编造现场服务 ID。无服务配置时可以完成设备及存储安装，但业务绑定状态必须为 `NOT_CONFIGURED`。
- 声明启用某业务消费者时，必须提供对应完整配置，并把绑定及正式账号验证纳入其启动门禁。
  不允许以空 `bindings` 返回整体“业务就绪”。
- 初始化仍优先复用已匹配主档、来源、世界对象和既有绑定；冲突报错，不覆盖。

主要修改位置：`.env.example`、`docker-compose.yml`、`scripts/dev-deploy.sh`、
`scripts/business-storage/device-cli.ts`、设备 bootstrap/context、相关部署检查与说明。

验收：原始模板仅填必需地址/凭据即可跑通范围一致的安装；初始化两次仅有一条目标主档、七条业务流；
配置进入容器后与数据库绑定一致。显式范围冲突、多范围 H3、缺参数及冲突绑定均有明确失败结果。

## 5. R2：正式账号、受控写入与原生业务存储就绪

### 5.1 受控设备接纳

保留 `resolveBusinessDeviceContext()` 的公共输入/返回结构及首次默认关联语义，
内部将管理员配置操作、运行时接纳和只读验证分开。

- 新增管理员维护的业务调用授权记录，关联数据库登录身份、数据范围、服务三元组、
  允许的设备集合及是否允许首次唯一设备选择。服务身份来自已确认部署配置。
- 接纳使用受控数据库函数。函数以原始数据库登录身份验证授权；不能靠调用者传入 scope、
  service key 或自行设置的 GUC 取得权限。`SESSION_USER` 与角色切换场景纳入测试。
- 查找优先级保持：显式设备 / 已有服务绑定优先；只有当前授权范围实际存在唯一启用主档时，
  才能首次默认选择并持久化绑定。存在第二台启用设备时，不通过缩小授权集合掩盖范围内歧义。
- 校验设备启用状态、范围和正式 WORLD_OBJECT 引用；冲突绑定不覆盖。
  SDAR 配置补充只能在授权且内容兼容时追加绑定修订；既有历史绑定不改写。
- 按服务/设备键串行化竞争并依赖唯一约束兜底；并发首次接入返回同一绑定或明确冲突。
- `verify` 使用只读事务，不要求 `FOR UPDATE`。`admit` 所需锁与写入封装在受控函数内。

函数使用专用 NOLOGIN 所有者、固定安全 `search_path` 和明确 schema 引用，撤销 PUBLIC 执行权限；
业务账号仅获所需函数 EXECUTE 和 schema USAGE，不授予设备主档/绑定的任意 INSERT、UPDATE。
不把本次修复描述为所有原生业务表已实现数据库级多租户隔离；原生域账号仍是受信运行账号。

### 5.2 目标、Mission 和统一查询

- 将 SDK 的目标创建/关联、Mission 身份登记、Execution—Mission 关联及统一读取接入同一授权边界。
  通过受控函数补齐所需权限，不简单向两个账号开放共享 schema 全表 DML。
- 每项写入验证调用域、设备、范围及 owner 实际存在，维持既有完整 owner key、幂等冲突和外键约束。
  跨域 lineage 读取仅返回该调用方获授权的设备/任务数据。
- 查询函数在同一事务设置范围，并检查登录授权；自设范围变量不能替代授权校验。
- 不对业务库增加全局默认 `device_id`；后续消费者仍将解析后的设备 ID 显式传给每次写入。

### 5.3 自动安装与保留数据升级

- 将正式 native installer 接入全新安装链路：
  配置/依赖预检 → 核心迁移 → 原生 SMPP/SDAR 迁移和新增 overlay → 账号/授权 → 设备及服务绑定 →
  正式账号验证 → 启动采集及声明启用的消费者。
- 为 SDAR 的 `public.vector` 提供正式数据库镜像依赖：锁定适配版本和来源摘要，补许可证/SBOM。
  新库由管理员安装扩展；保留库验证已有扩展版本/namespace，不自动搬迁扩展或替换数据库镜像。
- 新增显式安装模式：仅采集、共享业务存储、指定业务消费者就绪。全新默认安装包含两个固定业务 schema
  的正式表和独立初始账号；服务配置不完整时如实报告绑定未就绪。
- 现有密码只验证、不轮换。账号已存在但不受当前安装器管理、schema 非空且无合法安装账本、摘要冲突，
  均停止处理，不接管未知对象。
- 保留数据升级只执行明确待应用的追加迁移/overlay 和验证；不隐式重跑账号、设备或默认绑定初始化。
  权限修复由追加 SQL 生效，不要求用管理员重新生成账号密码。
- 核心迁移不得依赖尚未安装的原生业务表。依赖原生表的视图/函数由新增版本 overlay 安装，
  旧 overlay 不改写；同步更新安装清单、结构验证和按 domain 的验证能力。

主要修改位置：`database/migrations/`、`database/shared-business-storage/overlays/`、
`packages/integrations/device-business-storage/`、`scripts/business-storage/`、数据库镜像和 Compose 安装依赖。

验收：

1. 使用实际 `ugv_smpp_app`、`ugv_sdar_app` 登录完成单设备首次默认关联、重复解析及只读验证，
   两者关联同一正式主档；无 `42501`。
2. 两账号完成各自允许的目标/关联写入和统一查询；直接改设备、越权服务/设备/范围及伪造 owner 被拒绝。
3. 两设备并行接入互不混入；没有绑定的默认选择报歧义；禁用、缺引用、配置冲突和并发冲突均被拒绝。
4. 完整新安装重复执行不增加记录、不改变密码；086 保留数据升级前后的旧记录及历史摘要一致。
5. `ugv_smpp.provider_task`、`ugv_sdar.agent_task` 等正式对象及函数、序列、外键、search path 通过结构验证；

## 6. R3：修复旧 REST/MCP 的轨迹语义

采用一个共享的轨迹分析读口，复用已有不可变 tracklet 版本、SequenceSet、时间边界和缺口判定。
不在旧 analytics 中另加一套按相邻点时间差猜测连续性的规则。

- 从授权范围、对象、来源、采集会话、分析空间及规则版本确定输入；在一次一致读取中冻结实际使用的版本。
  多来源/多会话必须明确选择或返回歧义，不能平铺混合后计算。
- 距离只累计同一有效连续片段内部的移动；停留候选只能来自有效连续时间集合，缺口切断候选。
  偏离分析同样保留未知区间，不能跨缺口绘制并据此判断路径。
- 点数组保留兼容用途，但摘要须区分已观测部分、缺口、截断和覆盖范围。
  几何节点数不能作为原始证据样本数；零原始样本插值片段仍遵守既有证据语义。
- 投影尚未完成时返回诚实的 pending/不可用状态，不回退到会给出更强结论的旧计算。
  100,000 点等预算触发时明确截断，不能把截断窗口描述为完整任务轨迹。
- 保留既有路由及稳定字段；新增缺口/版本信息若违反严格合同，则新增版本化输出并显式标记旧字段语义。
  不以“兼容”为由继续提供跨缺口的停留或行驶距离。
- MCP `get_object_track` 与 REST 共用该结果，context 指向实际轨迹输入版本；
  不再将当前对象 worldVersion 当作历史轨迹的版本证明。

主要修改位置：`packages/runtime/src/trajectory-repository.ts`、`packages/trajectory-model/src/analytics.ts`、
`services/world-api/src/app.ts`、`services/world-mcp-server/src/server.ts` 和共享轨迹读口。

验收：两条相隔一小时的同位置记录不产生一小时连续停留；跨该缺口的约 85km 不计入连续行驶距离。
覆盖真实连续轨迹、重置、多会话、晚到修订、重复时间、开闭边界、无交集、截断、跨范围及缺失投影。
新版历史 Provider/STAS 与旧入口对相同冻结输入的覆盖与缺口一致，旧冻结结果及摘要保持不变。

## 7. R4：SSE 持久游标和完整恢复

使用数据库中的持久交付顺序，MQTT 作为及时唤醒信号；不把单次 10,000 条查询当作完整回放。

### 7.1 防止晚提交遗漏

- `world_version`、序列分配时刻及 `created_at` 均不能直接证明某个提交前缀已经闭合。
  不采用仅以 `(world_version, created_at, event_id)` 无限前推的方案来承诺无遗漏。
- 为已提交事件追加范围内的交付索引，索引只引用 `world_event`，不复制为新的业务事实库。
  原事件和公开事件内容保持不变。
- 事件事务内记录待追加项；追加器仅见已提交项。每个范围通过事务锁和计数行串行分配交付序号，
  索引追加与计数更新同事务提交。序号不是在事件原事务中提前分配的普通 sequence。
- 迁移为已有事件建立可重入待追加项；与新写入触发器/写入函数一起避免切换窗口遗漏。
  已经 MQTT 发布的旧事件也必须可回放；晚提交的低 worldVersion 事件获得新的交付位置。
- 追加器与 MQTT 发布解耦，使用有限连接和独立重试；可复用现有 worker 承载，不能阻塞历史查询执行槽。

### 7.2 恢复与资源边界

- 分页回放直到当前已提交交付位置，再持续读同一索引；broker 唤醒丢失时由定时查库补偿。
  单页上限是内存/SQL 预算，不是总回放上限。
- 保留 `id: eventId`，`Last-Event-ID` 在同一授权范围内解析到交付位置；游标、过滤器和范围一起验证。
  未知、已过期或越权游标返回明确错误；发生在响应头发出前，不能静默从最新位置开始。
- `sinceWorldVersion` 保留原筛选语义；标准重连以交付游标为准，不把版本阈值宣传为提交确认。
  同时提供两种恢复条件时明确优先级和冲突规则。
- 不依赖无限增长的内存 seen 集合。设置有限缓冲、`write()` 背压、连接关闭清理与心跳；
  慢消费者超过预算时显式中断并允许按最后收到的事件 ID 重连。
- 交付语义为可恢复、至少一次；客户端按 eventId 幂等。交付序号表示传输顺序，不能解释成事件时间顺序。
  本轮不自动清理事件/游标；将来保留期必须配套过期游标合同。
- 在现有受信部署下显式校验配置允许的范围；生产 profile 再结合可信身份校验。
  不能把客户端自报 scope 当作新认证机制。

验收：超过 10,000 条积压、同 worldVersion 多事件、并发晚提交、回放中新增事件、断网重连、broker 中断、
追加器崩溃重启和慢消费者均无永久遗漏。测试未知/跨范围/过滤器不兼容游标；验证重复允许且可去重。

| 089 | 持久事件交付待处理项、范围内游标及追加/读取函数 | 不修改已有事件内容；旧发布流程可继续运行 |

原生表相关 API 使用新的 GOWM overlay 版本和独立摘要，不能覆盖 `*_v1.sql` 的既有身份。
如 088 经实现证明不需数据库新增对象，则不创建空迁移，后续编号顺延并同步清单。

必需门禁：

- 新旧迁移摘要、001–086 → 新头保留数据升级、全新安装及重复安装；未知非空 schema 的拒绝路径。
- 原始默认配置的实际 Compose 接线、七条业务流与 reset_ack 策略校验、Gateway/H3 readiness。
- 两个正式登录账号的业务接入/关联/查询正向与越权负向测试。
- 旧轨迹语义及 SSE 恢复测试；相关 mapper/context 冻结、租约和 086 复用用例按受影响范围回归。
- 类型检查、相关单元/真实 PostgreSQL 集成检查和变更镜像构建。
  若更改了轨迹裁剪/重建 SQL 或索引，重跑其真实规模执行计划和已约定 SLO；无相关改变不重复整套压力测试。
- 安装器环境检查必须识别脚本读取的动态变量；必需数据库测试不允许 SKIP 后通过 required check。
- 更新源码/镜像/迁移交付清单，不把头版本硬编码停在 086；验证包入口、镜像摘要、源码摘要、校验和和可重复打包。
  保留旧包，不能覆盖后丢失回退来源。

随包更新 `PROJECT_STATUS.md`、部署指南、设备/业务交接、重置及历史并发说明，准确描述
CORE/TRACKLET/FINALIZATION/HISTORY；区分 LOCAL_VERIFIED、PACKAGE_VERIFIED、BUSINESS_ACCEPTED 和现场未验证状态。

## 9. 后续功能里程碑

以下项目覆盖本次审计中的扩展和证据缺口，但不阻塞 F01–F05 的局部修复发布。

### M1：真实跨仓业务闭环（C02）

- GOWM 先交付 R2 的 API/SDK、正式账号连接合同、幂等/owner 规则、双设备集成样例和可复核验收查询。
- SMPP、SDAR、UGV Provider 各仓先检查其最新代码，再列出实际缺失适配；旧交接文档的延期标记不能代替当前审计。
  其他仓运行时代码由独立获授权任务修改。
- 沿正常协议完成两个设备的 Task → 目标 → MCP Task → Execution → Mission → 统一查询，
  证明设备隔离、重复回执幂等、失败/未解析状态和重启恢复。
- 仅用已获授权的测试环境开展会产生动作的业务调用，禁止用直接插表或 fixture 冒充真实派发/回执。
  SACS→WSGS 验收保留真实 `PARTIAL/PROVISIONAL` 和 gap；没有 Finding 证据时不标业务验收通过。

### M2：完整历史轨迹 Artifact（C03 的基础能力）

- 先提供范围校验、版本固定、可分页/下载的完整轨迹读取；引用绑定精确 trajectory revision、
  完整冻结请求/快照及内容摘要，读取不能漂移到其他请求的最新结果。
- 返回分段、时间边界、缺口、原始证据计数及完整性，区分完整几何节点与原始观测。
  Artifact 不构成业务数据导出同步链，不新增轨迹事实权威。
- 规定预算、校验和、访问授权、有效期和保留期；验证预览→引用→完整读取的摘要一致性。
  旧公开合同保持兼容；解除消费者 lock 中对应非声明需要更新合同并提供真实读取证据。

### M3：可靠设备时间和显式会话切换（C04）

- 定义仿真 tick / 设备时间的单位、epoch、会话、时钟校准来源、漂移/不确定度与适用边界。
  新时钟模型版本经校准证据验证后才供新消息使用；缺少信息时保留 unresolved，不能猜时间。
- MQTT 到达代理模型继续兼容；校准、actor 和路由随采集会话冻结，不改写旧消息时间或旧轨迹。
  reset_ack 支持新模型前必须验证时间转换和观测边界，失败仍待处理。
- 仿真 UI reset 是否已发回执先检查外仓最新实现；必要时通过另行授权的仿真仓任务统一回执。
  GOWM 不伪造成功回执、不自动切换持久会话、不调大速度阈值来掩盖连续性问题。
- 验收覆盖批量迟到、积压、时钟重置/漂移、乱序回执、无校准和重复 reset。

### M4：通用采集配置和多范围 H3（C05、F01 的扩展）

- 将设备 profile、端点、topic、QoS、mapper 配置和允许 CRS 形成版本化运行合同；
  当前七条主题的机场仿真 profile 保留，不以删校验宣称支持实车或任意 CRS。
- 配置切换采用停止领取、处理已有消息、结束旧会话、验证配置并建立新会话的显式流程。
  双设备继续独立持久会话；管理命令不能改变旧 inbox/outbox 的身份和上下文摘要。
- 多范围 H3 另增正式聚合/投影/读取版本，键中包含 data scope，更新、删除、重建和授权都按范围处理。
  为已有数据受控重投影，验证两个范围同一个 H3 cell 不混入；达到隔离验收后才能移除单范围限制。

### M5：高级历史分析（C03 的扩展）

在 M2 和相应时间/输入合同具备后，逐项实施道路匹配、历史时空事件、最后交汇、历史信号/指标排名。
先检查相邻 Provider 仓的最新实现，GOWM 提供对应版本化读合同，不重复建立算法权威或擅自修改外仓。
每项分别固定规则/道路网络/信号版本、空间时间不确定度、缺口传播、预算及正反例，再更新消费者能力声明。

### M6：生产入口与长期运维

- 新增可选 production profile：沿用 Gateway 身份体系，落实旧 API/MCP 的可信入口或隔离、
  MQTT TLS/账号/ACL 和最小网络暴露。开发受信 LAN/VPN 模式显式保留，默认升级不影响现有依赖连接。
- 在已有日志、诊断和 MQTT metrics 基础上补队列等待、有效并发、续租失败、SSE 积压、连接池、存储增长告警。
- 备份/WAL/PITR、RPO/RTO、容量/分区/保留及 HA 分别形成实际交付和隔离恢复演练。
  涉及共享数据库/卷的部署变更单独审核，不能把手册命令或健康检查作为恢复能力验收。
- 不因容量治理删除仍被旧快照、轨迹或分析引用的不可变证据。

## 10. 上线、回退与完成判定

本计划完成后先交付可审阅代码、迁移、证据和新包；不自动执行远程操作。

后续获授权上线时，先只读确认当前范围、账号、原生安装账本、扩展、对象归属、容器与依赖，
再备份受影响数据并追加迁移。按依赖顺序更新涉及的 GOWM 服务；不执行 `down -v`、
不替换关联数据库容器或重建既有绑定、不运行默认账号初始化、不提升现场历史并发。
采集会话仅在配置/mapper 确需变化时按原有排空和新建流程切换。

数据库变更采用追加式兼容设计。故障时回退到已验证可读新 schema 的旧镜像或关闭新增功能，
保留新表和审计记录，不靠删除迁移、重写账本或恢复共享数据库来回退。
不能以旧版不安全的缺口分析或 SSE 静默丢事件作为无提示的降级路径。

本轮完成判定必须同时具备：F01–F05 的回归证据、实际业务账号接入、全新/保留安装、相关 CI、
新包一致性及逐项状态说明。M1–M6 未完成的部分维持明确延期或外部依赖状态。
现场部署、真实业务验收和生产资格仍分别记录，不能由本地通过推导为已完成。
